    vLLM 部署 MiniMax-M2 实战（4×RTX PRO 6000 Blackwell 容器场景 NCCL 排障全记录）¶

    一、背景¶

    这篇文章记录在 OpenBayes GPU 容器中，用 vLLM 把 MiniMax-M2 跑起来的完整过程。重点不是「照着官方文档抄命令」——官方 vllm_deploy_guide.md 写得很清楚，4 卡命令一行就能贴出来。重点是：在 容器 + 无 NVLink 的 PCIe-only 4 卡 RTX PRO 6000 Blackwell 这种官方文档没覆盖的组合下，按官方命令直接起会连续遇到两次 NCCL 错误，最终需要把 NCCL 强制退化到 loopback socket 才能跑通。

    我把整条故障链路、每一步的判断依据、最终 start.sh 的每一行配置原因都写下来，给下次遇到相同场景的人省时间。

    本次环境：

    项 值
    部署平台 OpenBayes 容器（SSH 端口 31063）
    GPU 4 × NVIDIA RTX PRO 6000 Blackwell（96GB）
    拓扑 PCIe-only，无 NVLink
    容器视角 GPU 0/½/3（宿主物理 0/2/6/7，被运行时重映射）
    共享内存 /dev/shm = 354 GB tmpfs
    模型路径 /openbayes/input/input0（平台预挂载）
    模型 MiniMax-M2，FP8 量化，62 层 / 256 experts MoE
    vLLM 0.20.1（/opt/venv/bin/vllm）
    Torch / CUDA 2.11.0+cu130 / CUDA 13.0
    NCCL 2.28.9+cuda13.0

    官方参考：

    • MiniMax-M2 Hugging Face
    • 模型自带 docs/vllm_deploy_guide.md（这次部署里的官方推荐命令就来自这里）
    • vLLM 官方文档
    • NCCL 环境变量参考

    二、模型与硬件勘察¶

    进容器先摸清三件事：模型是什么、GPU 是什么、官方推荐怎么起。

    1. 看模型目录与 config¶

    ssh root@ssh.openbayes.com -p31063 \
  'ls /openbayes/input/input0/ && echo "---GPU---" && nvidia-smi -L \
   && echo "---CONFIG---" && cat /openbayes/input/input0/config.json'

    关键输出：

    • 目录里有 125 个 model-XXXXX-of-00130.safetensors 分片（实际 125 个，序号到 124，后面解释为什么不是 130）。
    • 还有 configuration_minimax_m2.py / modeling_minimax_m2.py —— 模型有 自定义代码，启动必须加 --trust-remote-code。
    • GPU：4 张 NVIDIA RTX PRO 6000 Blackwell Server Edition。

    config.json 里几条关键信息：

    {
  "architectures": ["MiniMaxM2ForCausalLM"],
  "model_type": "minimax_m2",
  "dtype": "bfloat16",
  "hidden_size": 3072,
  "num_hidden_layers": 62,
  "num_attention_heads": 48,
  "num_key_value_heads": 8,
  "num_experts_per_tok": 8,
  "num_local_experts": 256,
  "max_position_embeddings": 204800,
  "quantization_config": {
    "fmt": "float8_e4m3fn",
    "quant_method": "fp8",
    "weight_block_size": [128, 128]
  }
}

    这告诉我：

    • MoE：256 个 expert，每 token 激活 8 个。
    • FP8 (e4m3) 量化，权重块大小 128×128。
    • 原生上下文 204,800 tokens。
    • TP 切分要兼顾 num_attention_heads=48 和 num_key_value_heads=8，4 卡（48/4=12 和 8/4=2）能整除，安全。

    2. 看 vLLM 是否就绪、写盘位置¶

    ssh root@ssh.openbayes.com -p31063 \
  'python -c "import vllm; print(vllm.__version__)"; which vllm; \
   ls -ld /openbayes/home /openbayes/output'
    • vllm 0.20.1，路径 /opt/venv/bin/vllm。
    • /openbayes/home 是 /output 的软链接 —— OpenBayes 容器里只有 /output 是持久化的，所有想跨重启留下来的东西都得写这里。

    3. 看官方推荐命令¶

    模型自带 docs/vllm_deploy_guide.md，4-GPU 推荐：

    SAFETENSORS_FAST_GPU=1 vllm serve \
    MiniMaxAI/MiniMax-M2.7 --trust-remote-code \
    --tensor-parallel-size 4 \
    --enable-auto-tool-choice --tool-call-parser minimax_m2 \
    --reasoning-parser minimax_m2_append_think

    把 HF 名换成本地路径 /openbayes/input/input0，再补上 --host 0.0.0.0 --port 8080 --served-model-name MiniMax-M2，就是第一版 start.sh。

    三、第一版 start.sh（按官方推荐裸起）¶

    #!/bin/bash
set -euo pipefail

MODEL_PATH="/openbayes/input/input0"
SERVED_NAME="MiniMax-M2"
HOST="0.0.0.0"
PORT="${PORT:-8080}"

export SAFETENSORS_FAST_GPU=1
export HF_HOME="${HF_HOME:-/output/.cache/huggingface}"
export VLLM_CACHE_ROOT="${VLLM_CACHE_ROOT:-/output/.cache/vllm}"
mkdir -p "$HF_HOME" "$VLLM_CACHE_ROOT"

exec vllm serve "$MODEL_PATH" \
    --served-model-name "$SERVED_NAME" \
    --trust-remote-code \
    --tensor-parallel-size 4 \
    --host "$HOST" --port "$PORT" \
    --enable-auto-tool-choice \
    --tool-call-parser minimax_m2 \
    --reasoning-parser minimax_m2_append_think

    写到 /openbayes/home/start.sh，chmod +x，启动方式：

    nohup setsid /openbayes/home/start.sh </dev/null >/output/vllm.log 2>&1 &

    几个 SSH 操作的小坑（实际踩到的）：

    1. ssh ... 'pkill ... && setsid ... &' 这种杀进程 + 后台启写在一条 SSH 命令里，pkill 杀掉 vllm 时偶发把 SSH 会话一起带断，后面的 setsid 没机会执行。经验：把 kill 和 start 拆成两次独立的 SSH，并且启动那次用 nohup setsid ... & exit 0，让 SSH 干净退出。
    2. nohup ... & + disown 在 bash -c 里其实没完全脱离会话，需要叠 setsid 才稳。

    第一次起来 30 秒就崩了。

    四、故障 1：NCCL error: unhandled system error¶

    4.1 现象¶

    /output/vllm.log 顶层显示：

    (APIServer pid=2550) RuntimeError: Engine core initialization failed.
                                   See root cause above. Failed core proc(s): {}

    这是壳错误。继续往上翻 worker 子进程：

    (Worker pid=3084) ERROR [multiproc_executor.py:870] WorkerProc failed to start.
...
(Worker pid=3084) File ".../vllm/distributed/device_communicators/pynccl.py",
                  line 142, in __init__
                      self.all_reduce(data)
...
(Worker pid=3084) RuntimeError: NCCL error: unhandled system error
                  (run with NCCL_DEBUG=INFO for details)

    调用栈是：init_worker_distributed_environment → PyNcclCommunicator.__init__ → 第一次 ncclAllReduce 就炸。

    4.2 判断¶

    unhandled system error 是 NCCL 通用兜底错，必须开 NCCL_DEBUG=INFO 看真实根因。在做这之前，先把环境摸清楚：

    ssh ... 'df -h /dev/shm; nvidia-smi topo -m; ls /dev/nvidia*'

    关键发现：

    • /dev/shm = 354 GB，不是共享内存太小。
    • nvidia-smi topo -m 显示 4 张卡两两全是 NODE（同 NUMA 节点的 PCIe），没有任何 NV# 行 —— 这台机器 4 卡之间没有 NVLink。
    • /dev/nvidia* 实际暴露 0、2、6、7 四个设备 —— 宿主有 8 卡，容器分到 4 个非连续物理 GPU，被 NVIDIA 容器运行时重映射成 0/½/3。

    这种 PCIe-only + 容器 GPU 重映射 的组合是 NCCL 默认握手最容易翻车的场景：NCCL 会先探测 P2P 通路，PCIe + 非连续 ID 这一步本身就不可靠。

    4.3 第一次修复（错误尝试）¶

    策略：禁掉 P2P，让 NCCL 走 SHM（/dev/shm 足够大）；同时禁 IB（容器没有 RDMA）；指定 socket 走 loopback；开 DEBUG 留证据。

    在 start.sh 顶部加：

    export NCCL_P2P_DISABLE=1
export NCCL_IB_DISABLE=1
export NCCL_SHM_DISABLE=0
export NCCL_NET_GDR_LEVEL=0
export NCCL_SOCKET_IFNAME=lo
export NCCL_DEBUG=INFO
export NCCL_DEBUG_FILE=/output/nccl.log

    重启 —— 仍然失败。但这次 /output/nccl.log 有内容了。

    五、故障 2：NCCL SHM 段名乱码¶

    5.1 现象¶

    /output/nccl.log 关键片段：

    NCCL INFO Bootstrap: Using lo:127.0.0.1<0>
NCCL INFO NCCL version 2.28.9+cuda13.0
NCCL INFO NCCL_P2P_DISABLE set by environment to 1
NCCL INFO NCCL_SHM_DISABLE set by environment to 0
NCCL INFO Channel 00 : 1[1] -> 2[2] via SHM/direct/direct
NCCL INFO Channel 01 : 1[1] -> 2[2] via SHM/direct/direct

NCCL WARN Call to open failed: No such file or directory
NCCL WARN Error while attaching to shared memory segment
         /dev/shm/nccl-�� (size 0), error: No such file or directory (2)
NCCL INFO transport/shm.cc:634 -> 2
NCCL INFO transport/shm.cc:203 -> 2
NCCL INFO transport.cc:231 -> 2

    注意段名 /dev/shm/nccl-�� —— 后面是乱码字符，正常应该是 nccl-<hash> 形态。说明 NCCL 在该容器环境下，SHM 段名传递在某一步被破坏，写出来的段名是空 / 乱码，自然 open(2) 报 ENOENT。

    /dev/shm 本身可读可写、空间足够；问题出在 NCCL ↔ 容器命名空间的某个 corner case（NCCL 2.28.9 + vLLM 0.20.1 + 这套容器组合）。修源码不现实，只能绕开 SHM 通道。

    5.2 判断¶

    日志里还有一条关键线索：

    NCCL INFO Check P2P Type isAllDirectP2p 0 directMode 0 isAllCudaP2p 1

    isAllCudaP2p=1 说明即便我们设了 NCCL_P2P_DISABLE=1，CUDA 层 P2P 其实是可用的。理论上后续可以切「开 P2P」让 NCCL 走 cudaMemcpy 直接拷贝。但当前任务目标是先稳定跑通，所以选最保守的路：P2P + SHM 都禁，强制走 loopback socket。性能差，但能跑。

    5.3 第二次修复（成功）¶

    把 NCCL_SHM_DISABLE 改成 1：

    export NCCL_P2P_DISABLE=1
export NCCL_SHM_DISABLE=1   # 关键改动
export NCCL_IB_DISABLE=1
export NCCL_NET_GDR_LEVEL=0
export NCCL_SOCKET_IFNAME=lo
export NCCL_DEBUG=INFO
export NCCL_DEBUG_FILE=/output/nccl.log

    重启，过 NCCL 这一关了。下面看到的告警是 Blackwell + PCIe-only 拓扑的预期行为，不是错误：

    WARNING [symm_mem.py:66] SymmMemCommunicator: Device capability 12.0 not
        supported, communicator is not available.
WARNING [custom_all_reduce.py:153] Custom allreduce is disabled because it's
        not supported on more than two PCIe-only GPUs.
    • 第一条：Blackwell 是 SM 12.0，对称内存通信器（symm mem）暂不支持，回落到普通 NCCL allreduce，不影响功能。
    • 第二条：custom allreduce 不支持「3 张以上 PCIe-only GPU」，自动回落到 NCCL allreduce，符合官方实现。

    六、最终版 start.sh¶

    #!/bin/bash
set -euo pipefail

# vLLM serving for MiniMax-M2 (FP8, 62L/256E MoE)
# Hardware: 4x RTX PRO 6000 Blackwell (96GB), no NVLink (PCIe only)
# Reference: /openbayes/input/input0/docs/vllm_deploy_guide.md

MODEL_PATH="/openbayes/input/input0"
SERVED_NAME="MiniMax-M2"
HOST="0.0.0.0"

# 端口选择（兼容 OpenBayes 模型部署 / 训练两种场景）：
#   - 模型部署（OPENBAYES_SERVING_PRODUCTION 非空）默认暴露 80
#   - 模型训练 / 交互式容器默认暴露 8080
#   - 显式传入 PORT=xxxx ./start.sh 仍可覆盖
if [ -n "${PORT:-}" ]; then
    :
elif [ -n "${OPENBAYES_SERVING_PRODUCTION:-}" ]; then
    PORT=80
else
    PORT=8080
fi

export SAFETENSORS_FAST_GPU=1

# Persist HF/vLLM caches under /output so they survive container restarts
export HF_HOME="${HF_HOME:-/output/.cache/huggingface}"
export VLLM_CACHE_ROOT="${VLLM_CACHE_ROOT:-/output/.cache/vllm}"
mkdir -p "$HF_HOME" "$VLLM_CACHE_ROOT"

# --- NCCL config for OpenBayes container, 4x RTX PRO 6000 Blackwell, no NVLink.
# Previous failures and their fix:
#   1) Default settings  -> "unhandled system error" at first ncclAllReduce
#   2) P2P off + SHM on  -> SHM segment name corrupted: "/dev/shm/nccl-<garbled>"
# Workaround: disable both P2P and SHM, force NCCL inter-rank over loopback socket.
# Performance trade-off: ~2-3x slower than P2P/SHM, but reliable.
export NCCL_P2P_DISABLE=1
export NCCL_SHM_DISABLE=1
export NCCL_IB_DISABLE=1
export NCCL_NET_GDR_LEVEL=0
export NCCL_SOCKET_IFNAME=lo
export NCCL_DEBUG=INFO
export NCCL_DEBUG_FILE=/output/nccl.log

exec vllm serve "$MODEL_PATH" \
    --served-model-name "$SERVED_NAME" \
    --trust-remote-code \
    --tensor-parallel-size 4 \
    --host "$HOST" --port "$PORT" \
    --enable-auto-tool-choice \
    --tool-call-parser minimax_m2 \
    --reasoning-parser minimax_m2_append_think

    每个参数的为什么：

    参数 / 环境变量 作用
    set -euo pipefail Shell 出错立刻退出，避免静默失败
    端口三段式（显式 PORT → 部署 80 → 训练 8080） 适配 OpenBayes 平台约定：模型部署默认对外端口是 80，模型训练 / 交互式容器是 8080。判定依据是平台注入的 OPENBAYES_SERVING_PRODUCTION 环境变量；仍保留 PORT=xxxx ./start.sh 显式覆盖能力
    SAFETENSORS_FAST_GPU=1 加速 FP8 safetensors 加载
    HF_HOME / VLLM_CACHE_ROOT → /output/.cache/* 把 vLLM 的 torch.compile 缓存落到持久化目录，下次启动跳过编译
    NCCL_P2P_DISABLE=1 PCIe-only + 容器 GPU 重映射，默认 P2P 不可靠
    NCCL_SHM_DISABLE=1 容器内 SHM 段名传递坏掉，禁掉
    NCCL_IB_DISABLE=1 容器没有 RDMA
    NCCL_NET_GDR_LEVEL=0 禁 GPUDirect RDMA
    NCCL_SOCKET_IFNAME=lo 单机 4 卡走 loopback，不走外网卡
    NCCL_DEBUG=INFO + NCCL_DEBUG_FILE 出问题留证据
    --trust-remote-code 模型有 modeling_minimax_m2.py
    --tensor-parallel-size 4 4 卡张量并行
    --tool-call-parser minimax_m2 官方 tool-use 解析器
    --reasoning-parser minimax_m2_append_think 把 <think>...</think> 段识别为 reasoning
    --served-model-name MiniMax-M2 OpenAI 协议里 "model": "MiniMax-M2"
    --host 0.0.0.0 --port 8080 监听容器内全部网卡 8080 端口

    十、性能基准（vllm bench serve）¶

    服务起稳后跑了官方自带的 vllm bench serve，目的不是和别人横向比，是把当前这套 NCCL-socket 退化配置下的性能基线记下来，下次调参（比如打开 P2P）有对比锚点。

    10.1 测试设置¶

    • 工具：vllm bench serve（vLLM 0.20.1 自带）
    • 数据集：random（合成 prompt，避免命中任何 prefix cache）
    • 输入 / 输出：每条 1024 input tokens / 256 output tokens
    • 请求数：50
    • 并发：1 / 16 / 32 三档
    • 协议：openai-chat（/v1/chat/completions）
    • 服务端：本文最终 start.sh，NCCL 走 loopback socket

    命令模板：

    vllm bench serve \
  --backend openai-chat \
  --base-url http://127.0.0.1:8080 \
  --endpoint /v1/chat/completions \
  --model MiniMax-M2 \
  --tokenizer /openbayes/input/input0 \
  --trust-remote-code \
  --dataset-name random \
  --random-input-len 1024 \
  --random-output-len 256 \
  --num-prompts 50 \
  --max-concurrency <1|16|32> \
  --save-result \
  --result-filename /output/bench/minimax-m2-c<N>.json

    10.2 实测结果¶

    指标 并发 1 并发 16 并发 32
    总耗时（秒） 619.27 125.90 81.50
    请求吞吐（req/s） 0.081 0.397 0.613
    输出吞吐（tok/s） 20.67 101.67 157.05
    总吞吐（in+out, tok/s） 106.41 523.43 808.57
    TTFT 中位（ms） 1376.3 491.1 491.7
    TTFT 均值（ms） 1462.3 636.6 600.2
    TTFT P99（ms） 1891.0 4581.5 800.4
    TPOT 中位（ms/tok） 42.82 138.41 168.06
    TPOT P99（ms/tok） 44.35 166.66 168.67
    ITL 中位（ms） 42.57 134.24 162.54
    E2E 延迟中位（ms） 12310 35783 43492

    全部 50/50 请求成功，failed=0。原始 JSON 在 /output/bench/minimax-m2-c{1,16,32}.json。

    10.3 读这张表¶

    1. 单流（并发 1）= 单用户体验上限：TTFT ~1.4s、TPOT ~42.8 ms/tok（约 23 tok/s 的解码速度），256 tokens 的完整回答 12.3 秒。这就是 NCCL 走 loopback socket 后的「最快」体验，符合一开始预估的「比 P2P/SHM 慢 2-3 倍」量级。
    2. 并发 16 → 32，吞吐还能涨：输出吞吐从 101.67 → 157.05 tok/s（+54%），总耗时从 125.90s → 81.50s（-35%）。说明 4×Blackwell 在当前配置下没被 NCCL 吃满，还有 batching 空间。
    3. 并发 16 的 TTFT P99 异常高（4581ms）：均值 636、中位 491、P99 4581 —— 这是典型的 prefill 排队尾巴。max_concurrent_requests=32（vLLM 实际容忍到 32），50 条请求堆进来时部分请求要等前一批 prefill 排空才有 KV slot。并发 32 反而 P99 只有 800ms，可能是并发 16 那一轮恰好命中了一个不利的批次组合 —— 这种规模（50 prompts）做尾延迟分析样本太少，TTFT P99 这一列只看趋势不要看绝对值。
    4. TPOT 随并发上升：42.8 → 138.4 → 168.1 ms/tok。这是 batching 的代价 —— 单流时 GPU 等不到下一个 token，并发时 attention/MoE kernel 一次算多 token，单 token 平均延迟变长但整体吞吐起来。
    5. KV cache 没成为瓶颈：4 卡聚合 GPU KV cache size: 443,008 tokens，本次测试最大同时驻留 1024+256=1280 tok × 32 并发 ≈ 4 万 tokens，离 44.3 万还差一个数量级。

    10.4 这组数据的边界¶

    • NCCL 配置：P2P off + SHM off + loopback socket。打开 P2P 后所有 throughput 指标都可能 1.5-2× 提升，本次没测。
    • 输入长度：固定 1024 tok。短输入（如 128/256）TTFT 会显著下降，长输入（如 8K/16K）TPOT 会上升 —— 不要把这里的数据当成「MiniMax-M2 在 Blackwell 上的通用值」。
    • dataset=random：每条 prompt 都是新的，不命中任何 prefix cache。真实业务有 system prompt 复用时，TTFT 会比这里好。
    • 50 prompts 样本量小：吞吐 / 中位数可信，P99 仅供参考。

    十二、后续可做的优化（按收益排序）¶

    1. 首 token 延迟从 ~50s 降到 ~15-20s：试 NCCL_P2P_DISABLE=0 + NCCL_SHM_DISABLE=1，让 NCCL allreduce 走 CUDA P2P（cudaMemcpy）而非 SHM/socket。NCCL 日志里 isAllCudaP2p=1 说明 P2P 通路是可用的，故障 1 是默认参数组合的问题，单独打开 P2P 可能就稳。改完务必跑 smoke test 验证。
    2. 跳过 torch.compile 重复编译：当前 VLLM_CACHE_ROOT=/output/.cache/vllm 已经把编译产物落盘，第二次启动时 compilation: 101.76 s 这段应该接近 0；但若每次都重编，检查容器 nvidia driver / CUDA / vLLM 版本是否变了（任何一项变化都会让 cache key 失效）。
    3. 升级 vLLM 到 nightly：官方文档专门提到「output garbled 现象需升级到 nightly（commit cf3eacf 之后）」。目前我们没遇到乱码，但如果后续要走生产，建议跟 nightly。
    4. 加上 --compilation-config '{"cudagraph_mode":"PIECEWISE"}'：官方文档 FAQ 提到 CUDA illegal memory access 时用这个兜底。当前没遇到，不加。
    5. 暴露端口：OpenBayes 容器里 :8080 仅容器内可达，对外要走平台的「暴露端口」功能；纯容器内 / 同节点其它进程访问无需配置。

    十三、给后人的几条经验¶

    1. 不要把 vllm 顶层的 RuntimeError: Engine core initialization failed 当成根因。它只是 APIServer 收不到 worker 就绪的壳错误，真正的报错在更上面的 worker 子进程栈里。
    2. 遇到 NCCL error: unhandled system error 第一件事是开 NCCL_DEBUG=INFO + NCCL_DEBUG_FILE，从原始日志找首条 WARN/ERROR。不开 DEBUG，你只能瞎猜。
    3. /dev/shm 不只是看大小，还要看 NCCL 能不能正确写段。这次 354 GB 完全够用，但段名乱码照样炸；不要看到 shm 够大就排除 SHM 嫌疑。
    4. nvidia-smi topo -m 出现满屏 NODE 没有 NV#，意味着你不能假设有 NVLink。从一开始就要做好 PCIe-only 的心理预期，相关 NCCL 参数提前准备。
    5. MoE + FP8 + 大模型，启动 25 分钟是正常的，不要中途 kill。20 分钟读权重 + 5 分钟 profiling/compile/graph capture，前面没崩就耐心等。挂监控的关键是日志过滤要同时包含成功信号和失败信号。
    6. OpenBayes 容器里所有想持久化的东西都写 /output。/openbayes/home 是它的软链，写哪个都行；其它路径重启就没了。
    7. SSH 后台启动用 nohup setsid ... </dev/null >log 2>&1 & exit 0，单独发一次。不要和 pkill 串在一起，否则 SSH 会话被 kill 带断、后续命令不执行。
