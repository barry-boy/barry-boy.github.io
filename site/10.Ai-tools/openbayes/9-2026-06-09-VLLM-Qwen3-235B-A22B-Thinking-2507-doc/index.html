    vLLM 部署 Qwen3-235B-A22B-Thinking-2507 实战记录¶

    背景¶

    这篇文章记录如何在 OpenBayes GPU 容器中，使用 vLLM 下载、启动、测试和调优 Qwen/Qwen3-235B-A22B-Thinking-2507。

    本次实际部署环境：

    • 部署平台：OpenBayes
    • GPU：8 卡 NVIDIA RTX PRO 6000
    • 下载源：ModelScope 国内源
    • 模型地址：ModelScope Qwen3-235B-A22B-Thinking-2507

    这个模型适合复杂推理、代码、数学、长文档分析等场景。它不是普通的小模型，部署时重点不是“命令能不能跑”，而是显存、上下文长度、并发、KV Cache 之间的平衡。

    官方模型卡里的关键信息如下：

    • 模型名称：Qwen/Qwen3-235B-A22B-Thinking-2507
    • 模型类型：Causal Language Model
    • 架构：Qwen3 MoE
    • 参数规模：总参数 235B，单次推理激活约 22B
    • Expert 数量：128 个 experts，每次激活 8 个
    • 原生上下文：262144 tokens
    • 模型精度：BF16
    • 模式限制：只支持 thinking mode
    • vLLM 建议版本：vllm>=0.8.5

    官方参考：

    • Qwen3-235B-A22B-Thinking-2507 Hugging Face
    • Qwen3-235B-A22B-Thinking-2507 ModelScope
    • ModelScope 模型下载文档
    • NVIDIA RTX PRO 6000 官方规格
    • vLLM Reasoning Outputs

    资源评估¶

    推荐硬件¶

    这个模型虽然是 MoE，每次只激活 22B 参数，但权重本身仍然需要加载完整 235B 参数。BF16 权重体积很大，所以生产部署建议优先使用 8 卡大显存机器。

    本次环境是 8 卡 RTX PRO 6000。如果是 RTX PRO 6000 Blackwell，单卡显存为 96GB，8 卡总显存约 768GB。实际进入 OpenBayes 容器后仍然要用 nvidia-smi 确认显存容量，因为历史上也有 RTX 6000 Ada 48GB 这一类相近命名的卡。

    推荐规格：

    场景 推荐 GPU 说明
    本次 OpenBayes 部署 8 * RTX PRO 6000 按 8 卡张量并行部署
    基础测试 8 * RTX PRO 6000 建议先从 64K/128K 上下文启动
    生产服务 8 * RTX PRO 6000 / H100 / H200 更适合长上下文和稳定并发
    262K 长上下文 8 卡 80GB+ 大显存 需要给 KV Cache 留足空间
    1M 超长上下文 总显存约 1000GB 级别 官方也提示需要极高显存

    如果只是想体验模型能力，不建议在本地强行裸跑。可以先用云平台、OpenBayes GPU 容器或者推理平台验证。

    显存和上下文关系¶

    vLLM 启动时最容易遇到的问题是 KV Cache 不够。上下文越长，KV Cache 占用越高。

    几个经验值：

    • --max-model-len 262144 是官方原生上下文，但对显存压力很大。
    • 如果 OOM，可以先降到 131072。
    • 如果只是 API 功能测试，可以先降到 32768 或 65536。
    • 不要一开始就追求 262K + 高并发，先让模型稳定起来。

    环境检查¶

    进入 GPU 容器或服务器后，先确认基础环境。

    nvidia-smi
python3 --version
pip --version
df -h

    建议 Python 版本使用 3.10 或 3.11。磁盘空间至少准备 600GB 以上，模型权重、缓存、临时文件都会占空间。

    模型下载¶

    如果是在 OpenBayes 中运行，有两种常见方式：

    1. 提前把 ModelScope 模型下载好，作为 OpenBayes 数据集或输入目录挂载。
    2. 在 OpenBayes 容器中直接从 ModelScope 下载到输出目录或持久化目录。

    如果模型已经作为输入挂载，路径通常类似：

    /openbayes/input/input0/Qwen3-235B-A22B-Thinking-2507

    如果需要在容器中下载，建议放到输出目录或持久化数据盘，例如：

    /openbayes/output/models/Qwen3-235B-A22B-Thinking-2507

    下面统一用变量管理路径。

    export MODEL_ID="Qwen/Qwen3-235B-A22B-Thinking-2507"
export MODEL_DIR="/openbayes/output/models/Qwen3-235B-A22B-Thinking-2507"
export MODELSCOPE_CACHE="/openbayes/output/modelscope-cache"

    这里为了可以省钱，大家可以先开CPU的机器把模型文件下载下来再来操作

    我的下载方法： 

    apt install screen
screen -R download
modelscope download \
  --model Qwen/Qwen3-235B-A22B-Thinking-2507 \
  --local_dir ./

ctrl +ad # 保存并退出

    过段时间就可以看到数据集下载的模型文件，在openbayes平台下载这个方法是通用的，有兴趣可以试试看。（原始模型的大小为470.21GB所以下载可能需要一段时间，推荐夜晚来做下载模型的操作，可以节约很多时间）

    安装依赖¶

    安装 vLLM¶

    官方建议 vllm>=0.8.5。为了避免 Qwen3 MoE 结构不支持，建议直接安装较新的 vLLM 和 transformers。

    python3 -m pip install -U pip

    启动服务¶

    最小可用启动命令¶

    先用适合 OpenBayes 8 卡 RTX PRO 6000 的保守参数启动，目标是跑通 OpenAI-compatible API。

    export MODEL_DIR="/openbayes/output/models/Qwen3-235B-A22B-Thinking-2507"

vllm serve "${MODEL_DIR}" \
  --host 0.0.0.0 \
  --port 8000 \
  --served-model-name Qwen3-235B-A22B-Thinking-2507 \
  --tensor-parallel-size 8 \
  --max-model-len 131072 \
  --dtype bfloat16 \
  --gpu-memory-utilization 0.85 \
  --max-num-seqs 1 \
  --enable-reasoning \
  --reasoning-parser deepseek_r1

    说明：

    • --tensor-parallel-size 8：使用 8 张 GPU 做张量并行。
    • --max-model-len 131072：先用 128K 上下文启动，更适合第一次在 OpenBayes 上验证。
    • --dtype bfloat16：匹配模型 BF16 权重。
    • --gpu-memory-utilization 0.85：不要一开始打满显存，给系统和碎片留空间。
    • --max-num-seqs 1：第一次启动先保证单请求稳定。
    • --enable-reasoning：启用 reasoning 输出。
    • --reasoning-parser deepseek_r1：官方模型卡给出的 vLLM 部署参数。
    • --served-model-name：给 API 暴露一个稳定模型名，避免客户端使用本地绝对路径。

    调优思路¶

    1. OOM 调优顺序¶

    如果启动时报 OOM，不要先怀疑模型文件。优先按下面顺序降配置：

    1. 降低 --max-model-len，例如 262144 -> 131072 -> 65536 -> 32768。
    2. 降低 --max-num-seqs，先设置为 1。
    3. 降低 --max-num-batched-tokens，例如 131072 -> 65536 -> 32768。
    4. 降低 --gpu-memory-utilization 到 0.80。
    5. 确认 --tensor-parallel-size 是否等于实际可用 GPU 数量。

    常见错误：

    The model's max seq len is larger than the maximum number of tokens that can be stored in KV cache

    处理方式：

    --max-model-len 131072
--max-num-seqs 1
--gpu-memory-utilization 0.85

    2. 长上下文调优¶

    长上下文的瓶颈通常不是权重，而是 prefill 和 KV Cache。

    建议：

    • 文档分析类任务使用 --enable-chunked-prefill。
    • --max-num-batched-tokens 不要无限增大，先从 65536 开始。
    • 长上下文场景优先保证单请求稳定，不要追求高并发。
    • 如果业务请求多数小于 32K，不要把服务默认配置成 262K，显存利用率会很差。

    3. 并发调优¶

    并发能力主要由 max_model_len、max_num_seqs、KV Cache 显存共同决定。

    建议做两套服务：

    服务类型 max_model_len max_num_seqs 用途
    short-context 32768 8 到 32 日常问答、短 prompt
    long-context 131072 或 262144 1 到 2 长文档、复杂推理

    这样比一个服务同时承担所有请求更稳定。

    4. Thinking 输出调优¶

    这个模型只支持 thinking mode。官方说明默认 chat template 会自动包含 <think>，所以输出里只有 </think> 而没有显式 <think> 开始标签是正常现象。

    如果客户端只需要最终答案，可以在应用层只展示 content 字段，不展示 reasoning 字段。

    如果需要限制思考长度，可以结合 vLLM reasoning 参数和请求侧 max_tokens 做控制。实际生产中建议先限制 max_tokens，避免一次请求长时间占满 GPU。

    请求示例：

    curl http://127.0.0.1:8000/v1/chat/completions \

  -d '{
    "model": "Qwen3-235B-A22B-Thinking-2507",
    "messages": [
      {
        "role": "user",
        "content": "请分析一次 Kubernetes 集群 CoreDNS 延迟升高的排查路径。"
      }
    ],
    "temperature": 0.6,
    "top_p": 0.95,
    "max_tokens": 4096
  }'

    常见问题¶

    1. KeyError: qwen3_moe¶

    原因：transformers 版本过低。

    处理：

    python3 -m pip install -U "transformers>=4.51.0"

    2. CUDA out of memory¶

    处理顺序：

    --max-model-len 65536
--max-num-seqs 1
--gpu-memory-utilization 0.80
--max-num-batched-tokens 32768

    如果仍然不行，检查是否有其他进程占用 GPU：

    nvidia-smi

    3. API 返回模型名不是客户端传的名字¶

    启动时加：

    --served-model-name Qwen3-235B-A22B-Thinking-2507

    客户端请求统一使用：

    "model": "Qwen3-235B-A22B-Thinking-2507"

    4. 输出里没有 <think> 开始标签¶

    这是正常现象。官方说明该模型默认 chat template 会自动包含 <think>，输出中只有 </think> 不代表错误。

    5. 长上下文请求非常慢¶

    这是正常现象。长上下文会让 prefill 阶段非常重。

    优化方向：

    • 开启 --enable-chunked-prefill。
    • 降低 --max-num-batched-tokens。
    • 将短请求和长请求拆成两个服务。
    • 在业务层限制用户输入长度。

    运维建议¶

    生产环境建议至少做这些限制：

    • API 网关层限制请求体大小。
    • 限制单请求 max_tokens。
    • 根据业务拆分 short-context 和 long-context 服务。
    • 监控 GPU 显存、GPU 利用率、请求延迟、队列长度。
    • 模型目录只读挂载，避免运行时误删。
    • 升级 vLLM 前先保留旧镜像，灰度验证 thinking 输出格式。

    Prometheus 监控可直接抓 vLLM 指标端点，常见关注项：

    • 请求总数
    • 首 token 延迟
    • 输出 token 速率
    • GPU KV Cache 使用率
    • running / waiting 请求数

    总结¶

    Qwen3-235B-A22B-Thinking-2507 的部署核心是显存规划。推荐路径是：

    1. 先通过 ModelScope 国内源下载模型并确认文件完整。
    2. 使用 vllm>=0.8.5 和较新的 transformers。
    3. 先用 --max-model-len 65536 或 131072 跑通。
    4. 稳定后再提高到 262144。
    5. 短请求和长上下文请求拆分部署。
    6. 1M 上下文只作为专项实验，不作为默认生产配置。

    GPU0  X    NODE NODE NODE SYS  SYS  SYS  SYS   # NUMA0
GPU4  SYS  SYS  SYS  SYS  X    NODE NODE NODE  # NUMA1

    SYS 表示需要跨 NUMA 通信，会严重拖慢 TP all-reduce。这是后面调优思路的关键背景。

    测试方法¶

    测试目标分两个：

    1. 单流速度：测 TTFT（首 token 延迟）和稳态生成速度（tokens/s）
    2. 并发吞吐：测整机在不同并发下的总吞吐与延迟分布

    所有测试都走 /v1/chat/completions 的 SSE 流式接口，从客户端实际感受的角度量。

    脚本 1：单流 TTFT + tok/s¶

    保存为 bench_vllm.py：

    #!/usr/bin/env python3
"""Benchmark vLLM OpenAI-compatible endpoint: TTFT and output tokens/s."""
import json
import sys
import time
import urllib.request

URL = "https://lixie-9v3cchvt8fii.gear-c1.openbayes.net/v1/chat/completions"
MODEL = "Qwen3-235B-A22B"


def run(prompt: str, max_tokens: int, enable_thinking: bool, label: str) -> dict:
    body = {
        "model": MODEL,
        "messages": [{"role": "user", "content": prompt}],
        "max_tokens": max_tokens,
        "temperature": 0.7,
        "stream": True,
        "stream_options": {"include_usage": True},
        "chat_template_kwargs": {"enable_thinking": enable_thinking},
    }
    req = urllib.request.Request(
        URL, data=json.dumps(body).encode(),
        headers={"Content-Type": "application/json"}, method="POST",
    )

    t_start = time.perf_counter()
    t_first = None
    content_chars = reasoning_chars = chunk_count = 0
    usage = None
    finish_reason = None

    with urllib.request.urlopen(req, timeout=600) as resp:
        for raw in resp:
            line = raw.decode().strip()
            if not line or not line.startswith("data:"):
                continue
            payload = line[5:].strip()
            if payload == "[DONE]":
                break
            try:
                evt = json.loads(payload)
            except json.JSONDecodeError:
                continue
            if evt.get("usage"):
                usage = evt["usage"]
            for ch in evt.get("choices", []) or []:
                delta = ch.get("delta", {}) or {}
                got = False
                if delta.get("content"):
                    content_chars += len(delta["content"]); got = True
                if delta.get("reasoning"):
                    reasoning_chars += len(delta["reasoning"]); got = True
                if got and t_first is None:
                    t_first = time.perf_counter()
                if got:
                    chunk_count += 1
                if ch.get("finish_reason"):
                    finish_reason = ch["finish_reason"]

    t_end = time.perf_counter()
    ttft = (t_first - t_start) if t_first else None
    total = t_end - t_start
    gen = (t_end - t_first) if t_first else None
    out_tokens = (usage or {}).get("completion_tokens")
    tps_gen = (out_tokens / gen) if (out_tokens and gen and gen > 0) else None

    print(f"\n=== {label} (thinking={enable_thinking}, max_tokens={max_tokens}) ===")
    print(f"prompt_tokens     : {(usage or {}).get('prompt_tokens')}")
    print(f"completion_tokens : {out_tokens}")
    print(f"finish_reason     : {finish_reason}")
    print(f"TTFT              : {ttft:.3f}s" if ttft else "TTFT              : n/a")
    print(f"total wall time   : {total:.3f}s")
    if gen is not None:
        print(f"generation window : {gen:.3f}s")
    if tps_gen is not None:
        print(f"throughput (gen)  : {tps_gen:.2f} tok/s")

    return {"label": label, "ttft": ttft, "gen": gen,
            "out_tokens": out_tokens, "tps_gen": tps_gen}


def main() -> int:
    short = "用一段话（约200字）介绍一下分布式系统的CAP定理。"
    long = ("请详细解释 Kubernetes 的调度器是如何工作的，包括 predicate、priority、"
            "preemption、以及 scheduling framework 的扩展点。要求覆盖原理、典型场景与"
            "常见问题，约600字。")
    runs = [
        run(short, 256, False, "short / no-think"),
        run(long, 512, False, "long  / no-think"),
        run(short, 512, True, "short / think"),
    ]
    print("\n=== Summary ===")
    print(f"{'label':<22} {'TTFT(s)':>8} {'gen(s)':>8} {'tokens':>8} {'tok/s':>8}")
    for r in runs:
        f = lambda x, fmt=".2f": format(x, fmt) if x else "n/a"
        print(f"{r['label']:<22} {f(r['ttft']):>8} {f(r['gen']):>8} "
              f"{str(r['out_tokens']):>8} {f(r['tps_gen']):>8}")
    return 0


if __name__ == "__main__":
    sys.exit(main())

    脚本 2：并发吞吐扫描¶

    保存为 bench_concurrent.py，用线程池模拟 1 / 2 / 4 / 8 / 16 并发：

    #!/usr/bin/env python3
"""Concurrent benchmark: aggregate throughput at various concurrency levels."""
import concurrent.futures as cf
import json
import time
import urllib.request

URL = "https://lixie-9v3cchvt8fii.gear-c1.openbayes.net/v1/chat/completions"
MODEL = "Qwen3-235B-A22B"
PROMPT = "请用大约300字详细说明 TCP 三次握手的过程、目的与可能的异常情况。"
MAX_TOKENS = 400


def one_request(idx: int) -> dict:
    body = {
        "model": MODEL,
        "messages": [{"role": "user", "content": PROMPT}],
        "max_tokens": MAX_TOKENS,
        "temperature": 0.7,
        "stream": True,
        "stream_options": {"include_usage": True},
        "chat_template_kwargs": {"enable_thinking": False},
    }
    req = urllib.request.Request(
        URL, data=json.dumps(body).encode(),
        headers={"Content-Type": "application/json"}, method="POST",
    )
    t_start = time.perf_counter()
    t_first = None
    out_tokens = None
    with urllib.request.urlopen(req, timeout=600) as resp:
        for raw in resp:
            line = raw.decode().strip()
            if not line.startswith("data:"):
                continue
            payload = line[5:].strip()
            if payload == "[DONE]":
                break
            try:
                evt = json.loads(payload)
            except json.JSONDecodeError:
                continue
            if evt.get("usage"):
                out_tokens = evt["usage"].get("completion_tokens")
            for ch in evt.get("choices", []) or []:
                delta = ch.get("delta", {}) or {}
                if (delta.get("content") or delta.get("reasoning")) and t_first is None:
                    t_first = time.perf_counter()
    t_end = time.perf_counter()
    return {"idx": idx,
            "ttft": (t_first - t_start) if t_first else None,
            "total": t_end - t_start,
            "tokens": out_tokens}


def run_level(concurrency: int) -> None:
    print(f"\n--- concurrency={concurrency} ---")
    t0 = time.perf_counter()
    with cf.ThreadPoolExecutor(max_workers=concurrency) as ex:
        results = list(ex.map(one_request, range(concurrency)))
    wall = time.perf_counter() - t0
    ttfts = sorted(r["ttft"] for r in results if r["ttft"])
    totals = sorted(r["total"] for r in results)
    sum_tok = sum(r["tokens"] for r in results if r["tokens"])
    print(f"wall time          : {wall:.2f}s")
    print(f"aggregate tok/s    : {sum_tok / wall:.2f}")
    if ttfts:
        print(f"TTFT p50/p95/max   : {ttfts[len(ttfts)//2]:.2f}s / "
              f"{ttfts[int(len(ttfts)*0.95)-1]:.2f}s / {ttfts[-1]:.2f}s")
    print(f"total p50/p95/max  : {totals[len(totals)//2]:.2f}s / "
          f"{totals[int(len(totals)*0.95)-1]:.2f}s / {totals[-1]:.2f}s")


if __name__ == "__main__":
    for c in (1, 2, 4, 8, 16):
        run_level(c)

    两个脚本都只用标准库，本地 python3 bench_vllm.py 即可运行。

    基线测试（原始配置）¶

    调优前服务启动参数：

    --tensor-parallel-size 8
--max-model-len 262144            # 256K 上下文
--gpu-memory-utilization 0.95
--enable-expert-parallel
--reasoning-parser qwen3

    单流结果：

    场景 TTFT 生成耗时 tokens tok/s
    短 prompt / 不思考 1.57s 6.50s 256 39.37
    长 prompt / 不思考 1.64s 13.03s 512 39.31
    短 prompt / 思考模式 1.01s 12.97s 512 39.48

    三种场景速度几乎一致，单流稳定在 ~39 tok/s。

    瓶颈分析¶

    为什么单流只有 ~39 tok/s？通过 SSH 进容器收集硬件和负载信息：

    nvidia-smi --query-gpu=memory.used,utilization.gpu --format=csv
nvidia-smi topo -m
ps -ef | grep vllm

    主要发现：

    1. 8 卡 TP + 无 NVLink 是最大瓶颈。每个 decode step 都要做 all-reduce，跨 NUMA 走 QPI 的代价远高于 NVLink。这就是单流上限被压在 ~39 tok/s 的根本原因。
    2. max_model_len=262144 把 KV cache 池吃光。显存利用率 0.95，权重已经占掉每卡 92 GB，留给 KV cache 的空间只够 batch 1–2，等于把整机并发能力废了。
    3. --enable-expert-parallel 在 TP=8 跨 NUMA 场景下，每个 token 的 top-8 expert 路由极大概率跨 NUMA，又一次 all-to-all 走 QPI。
    4. gpu-memory-utilization=0.95 太激进，留给 CUDA graph / NCCL buffer 只有 5%，容易触发 graph fallback。

    失败的调优尝试：TP=4 单 NUMA¶

    第一个想法是：把 8 卡 TP=8 拆成两个 TP=4 实例，每组在自己的 NUMA 内通信，单流速度可以提升 30–60%。

    # 想象中的实例 1
CUDA_VISIBLE_DEVICES=0,1,2,3 vllm serve ... --tensor-parallel-size 4

    实际启动直接 OOM：

    ERROR ... gpu_model_runner.py:4877] Failed to load model -
not enough GPU memory. ... CUDA out of memory.
Tried to allocate 384.00 MiB. GPU 2 has a total capacity of
94.97 GiB of which 98.06 MiB is free.

    原因复盘：235B bf16 ≈ 470 GB 权重。TP=8 时每卡 ~60 GB 权重，剩 36 GB 给 KV cache 和 buffer，能跑；TP=4 每卡需 ~117 GB，但单卡只有 96 GB，物理装不下。要走 TP=4 必须先做量化（INT8/AWQ/GPTQ）把权重砍到 ~120 GB 才行。

    回滚到 TP=8。记下教训：动并行策略之前先算权重显存账。

    最终落地配置（TP=8 + 其他优化）¶

    保留 TP=8，但把其他三件事做了：

    1. MAX_MODEL_LEN：262144 → 32768（不影响 99% 业务场景，KV cache 池扩大数倍）
    2. GPU_MEM_UTIL：0.95 → 0.92（留 8% 给 CUDA graph）
    3. 新增 --enable-chunked-prefill --enable-prefix-caching
    4. 关闭 --enable-expert-parallel（8 卡跨 NUMA 时反而是负优化）

    最终 start.sh（节选关键部分）：

    #!/usr/bin/env bash
set -euo pipefail

# 32K 上下文：避免 256K 把 KV cache 吃光，并发能力显著提升
MAX_MODEL_LEN="${MAX_MODEL_LEN:-32768}"
# 0.92 留 8% 给 CUDA graph / NCCL buffer
GPU_MEM_UTIL="${GPU_MEM_UTIL:-0.92}"
ENABLE_REASONING="${ENABLE_REASONING:-1}"
REASONING_PARSER="${REASONING_PARSER:-qwen3}"
# 长 prompt / 多轮对话场景显著降 TTFT
ENABLE_CHUNKED_PREFILL="${ENABLE_CHUNKED_PREFILL:-1}"
ENABLE_PREFIX_CACHING="${ENABLE_PREFIX_CACHING:-1}"
# 8 卡跨 NUMA 时关闭 expert parallel，避免额外 all-to-all
ENABLE_EXPERT_PARALLEL="${ENABLE_EXPERT_PARALLEL:-0}"

EXTRA_ARGS=()
[ "${ENABLE_REASONING}" = "1" ] && EXTRA_ARGS+=(--reasoning-parser "${REASONING_PARSER}")
[ "${ENABLE_CHUNKED_PREFILL}" = "1" ] && EXTRA_ARGS+=(--enable-chunked-prefill)
[ "${ENABLE_PREFIX_CACHING}" = "1" ] && EXTRA_ARGS+=(--enable-prefix-caching)
[ "${ENABLE_EXPERT_PARALLEL}" = "1" ] && EXTRA_ARGS+=(--enable-expert-parallel)

exec vllm serve "${MODEL_PATH}" \
    --served-model-name "${SERVED_NAME}" \
    --host 0.0.0.0 --port 8080 \
    --tensor-parallel-size 8 \
    --max-model-len "${MAX_MODEL_LEN}" \
    --gpu-memory-utilization "${GPU_MEM_UTIL}" \
    --trust-remote-code \
    "${EXTRA_ARGS[@]}"

    cp /openbayes/home/start.sh /openbayes/home/start.sh.bak.$(date +%Y%m%d-%H%M%S)

    调优后的真实数据¶

    单流（与基线对照）¶

    配置 单流 tok/s
    基线（256K + EP + 0.95） 39.4
    优化（32K + chunked prefill + prefix cache + 0.92） 43.8
    提升 +11%

    单流的提升不大，因为单流瓶颈仍然是跨 NUMA all-reduce。要再上一个台阶必须换硬件（NVLink）或换量化（缩小 TP）。

    并发吞吐扫描（新配置）¶

    并发 整机 tok/s 单流均速 TTFT p50 总耗时
    1 38 38 1.24s 10.4s
    2 67 34 1.28s 11.9s
    4 124 32 1.86s 12.9s
    8 155 19 1.33s 20.7s
    16 403 26 1.49s 15.9s

    关键洞察¶

    1. 整机吞吐从 ~39 → ~403 tok/s（约 10×）。单流提升只有 11%，但并发场景天差地别。原配置 256K 上下文几乎只能跑 batch 1，并发能力被完全废掉了，这才是 KV cache 优化的真实价值。
    2. 并发 16 是当前甜点：整机 403 tok/s，TTFT p50 仍稳定在 1.5s。生产侧推荐客户端并发设到 ≥16。
    3. 并发 8 出现谷底（155 tok/s < 124×2）：怀疑撞上了某个 KV cache 准入门槛或 prefill window 满载，建议跳过这个并发点。后续可以从 vLLM /metrics 里的 running / waiting / kv_cache_usage_perc 三个指标做进一步排查。

    踩坑速查¶

    现象 根因 解决
    TP=4 启动 OOM 235B bf16 权重 ~470 G，TP=4 每卡需 ~117 G > 96 G 单卡上限 走 TP=8，或先做 INT8/AWQ 量化
    pkill vllm 后 SSH 断开 vLLM 多进程被一锅端时会牵连 sshd 子 shell 等 8–10 秒重连，检查 nvidia-smi --query-compute-apps 清残留
    进程死了但显存没释放 NVIDIA driver 对孤儿 VLLM::Worker 回收有延迟 nvidia-smi --query-compute-apps=pid 找 PID 强杀
    chat 接口返回 content=null，全在 reasoning 字段 vLLM 启了 --reasoning-parser qwen3，把 <think> 内容分流到 reasoning_content 客户端同时读 delta.content 和 delta.reasoning；或启动时去掉 reasoning parser
    短 prompt 第一次请求 50s 才出 100 token 冷启动 + CUDA graph 编译 热起来后稳定 ~43 tok/s，可在服务上线时做一次 warm-up

    仍然可以继续做的事¶

    1. 量化版模型：INT8/AWQ 把权重砍到 ~120 G 后能上 TP=2 单 NUMA，单流速度大概率翻倍，整机吞吐再 2–3×。可优先关注 Qwen 官方或社区是否有 Qwen3-235B-A22B-AWQ / -Int8 发布。
    2. vLLM 升级：0.20.1 → 0.21+，新版本有 Blackwell 的 fused MoE kernel。
    3. 并发 8 退化原因：抓 vLLM /metrics 看 kv_cache_usage_perc 与排队长度，确认是 KV 准入还是 prefill chunk 大小问题。
    4. 拆分双实例：等量化版本就绪后，按 NUMA 拆 GPU0-3 / GPU4-7 两个独立 vLLM 实例，前面挂 nginx 做轮询，可同时获得"单流更快 + 整机更高"。

    一段话总结¶

    这次调优的核心不是某个魔法参数，而是搞清楚硬件拓扑（无 NVLink、跨 NUMA）和模型规模（235B bf16）共同决定了"TP=8 是唯一可行路径，但 KV cache 配置直接决定并发吞吐"。256K 上下文不是免费的，它在用整机并发能力换上下文容量。 业务真实需要 32K 就配 32K，把省下的显存全给 KV cache，整机产能立刻 10 倍。
